# Agent 执行与故障回放

用户同时要查 V200 团购券，并提交 A300 退款申请。订单查询第一次超时，退款工单写入后连接又中断。
Agent 可以查询原工单确认状态，客户仍按原审批流程处理，支付端使用工单 ID 保证幂等。

| 情况 | 执行层处理 |
| --- | --- |
| 白名单只读工具遇到临时故障 | 本次调用允许再试一次，重试前重新检查剩余时间 |
| 参数错误、未找到记录 | 当前调用返回具体错误码，相同调用受重复上限控制 |
| 写工具的结果未确认 | 返回 outcome_unknown，允许只读核实，拦截同一轮后续工具批次提交的写操作 |
| 主模型没有可显示文本或可解析的调用 | 剩余时间和调用额度允许时，每轮最多重试一次。用原对话及工具结果重发模型请求；再次失败则明确结束本轮 |
| 同一响应同时含可解析和损坏的调用 | 保留可解析的调用，剔除损坏的调用，防止下一次模型请求带上没有对应结果的调用 ID |
| 主模型传输超时 | 用明确的停止原因结束对话轮次，工单状态仍由业务库提供 |

每轮默认最多 10 次主模型调用、16 个逻辑工具位置，同名同参最多 2 次。一个允许重试的只读工具位置最多执行 2 次。
对话模型及工具内的证据核查使用剩余时间约束各个 HTTP I/O 阶段。120 秒是协作式时间预算，同步工具和已落库的业务动作会按自身的边界完成。

## 运行轨迹

服务端日志以 agent_runtime 开头，按 turn_id 查询。日志记录模型与工具尝试、延迟、错误码、已知的业务状态、停止原因和 HTTP/SSE 结尾。
模型供应商返回用量时记录输入与输出 token。日志字段使用工具名和事件类型，工具参数、原始提示和完整工具输出留在对应业务权限范围内。
模型尝试另记供应商停止原因、是否含文本和可解析／损坏的调用数。模型重试计入同一轮的 10 次默认调用上限。
供应商内容过滤会按明确原因结束本轮。被丢弃的空响应和损坏调用不会写入对话历史。

## 本地复现

```bash
python -m pytest tests/test_agent_runtime.py -q -o junit_logging=log --junitxml=work/agent-runtime/fault-tests.xml
```

- **混合任务与丢回执。** 使用真实图、订单库、券库和模拟退款网关。首次订单查询超时后重试成功。提交已落库但模拟丢掉回执，重复写请求被拦截，通过查询拿到原工单。按原权限批准后，两次执行请求只生成一笔退款。把测试中的工具响应回放到图中，确认可复现相同的工具结果。
- **重复错误。** 同时查工单进度和团购券，脚本模型两次给查券工具传入相同的不合法时间。每次只执行一回，第三次被循环上限拦截。
- **模型超时。** HTTP mock transport 观察对话模型和证据核查实际收到的 I/O 超时。验证都能继承 2 秒内的剩余时间，且各只发一次请求。
- **模型空响应与坏参数。** 通过脚本模型和 HTTP mock 注入空输出、只含损坏 JSON 的调用及混合批次。检查重试计数、截止时间、SSE 收尾与后续请求中的工具配对。混合业务回归也覆盖写入回执丢失后插入一次空回复，确认重试后的写操作仍被拦截。

回放使用临时数据库、脚本模型和记录在测试内的合成响应。它验证执行层的故障处理。真实模型如何在收到错误后选择恢复动作，由[恢复行为配对评测](agent-recovery-evaluation.md)验证。
