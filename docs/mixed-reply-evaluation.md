# 混合任务答复准确性盲测

本次评测检查客服回复里的**当前状态、事实和操作指引**。同一轮对话会独立记录 SQLite 的工单状态和模型的最终答复。例如，争议可能确实已经进入复核，但答复仍可能让用户重复提交。

## 协议

1. 冻结新的合成对话、数据库预期和答复命题，为数据集记录 SHA-256。待测模型只收到用户消息、正常对话历史与业务工具结果。
2. 复用前一轮的 DeepSeek、混合任务工具子集和执行边界。每个场景使用独立的 SQLite 和模拟支付。该设置衡量混合任务，完整生产提示与知识库未接入这次试验。
3. 生成只含不透明轮次编号、用户输入、最终答复和待判命题的审阅包。审阅者看不到命题的预期真假、数据库判分和场景名。输出逐条记录模型是否在答复中认可该命题，并保留能核查的原文。
4. 评分器检查轮次、命题和引用是否完整，并验证数据集摘要。需要明确说明的事实遗漏即失败。矛盾或语义含糊需要标记，不能自动算作通过。

例如，复述「你问是不是已经退款」不构成到账断言，「还未退款」可作为明确的否定或未到账陈述。「查看争议进展」与「再次提交争议」分别判定。普通退款的确认责任也要和券争议操作分开。

## 首轮结果

在 10 个新场景、13 轮合成对话中，DeepSeek 共调用 51 次，供应商返回 111,723 Token 的完整用量。回复由两份独立的模型辅助审阅标注。72 项命题中有 70 项初判一致，另两项逐句复核。原文和分歧的处理依据见 [机器可读结果](evaluation/mixed-reply-holdout-v2-result.json)。

| 指标 | 结果 |
| --- | ---: |
| 数据库与工具判分 | 9/10 场景，11/13 轮 |
| 回复判分 | 7/10 场景，9/13 轮 |
| 业务与回复均通过 | 7/10 场景，9/13 轮 |
| 业务通过、回复未通过 | 2 个场景，2 轮 |
| 逐项回复命题 | 67 项通过，4 项失败，1 项不明确 |
| 实际退款流水、未确认的新增争议 | 各 0 |

- **A300 多说了一层审批。** 工单需要申请人确认，回复正确指出需要点确认卡片，却又说随后由主管处理。这一额外步骤会让用户误判流程。
- **券退款指引互相冲突。** V200 的复核结论当时支持申请。回复先给出正确的「联系售后」，随后把该申请引向普通订单退款工具。最终标注为不明确。
- **A400 错报超期，影响后续撤回。** 答复声称超过七天，没给明确要求退款的用户建单。下一轮只取消了登记。另用相同种子的独立数据库复查，A400 的只读资格结果为可退。
- **新证据场景正常刷新。** 商家补传后，旧结论失效。工具先返回待重新观察，再读到了记录吻合且尚待重新复核的结果。回复保留了这一状态，也没有把商家版本当流水条数。

首次运行保存第九个场景时遇到 Windows 文件共享冲突。对比已落盘报告和完整临时文件后保留前九个场景，只补跑最后一个。报告保存增加了有限重试，生产 Agent 的提示和工具未因本次结果而调整。

## 复现

```bash
python -m evaluation.mixed_holdout_eval --with-model --dataset docs/evaluation/mixed-reply-holdout-v2.json --output work/reply-holdout/new-run.json
python -m evaluation.mixed_reply_score packet --dataset docs/evaluation/mixed-reply-holdout-v2.json --run work/reply-holdout/new-run.json --output work/reply-holdout/new-packet.json
python -m evaluation.mixed_reply_score score --dataset docs/evaluation/mixed-reply-holdout-v2.json --run work/reply-holdout/new-run.json --audit work/reply-holdout/new-audit.json --output work/reply-holdout/new-score.json
```

第一条命令会使用 DeepSeek API 额度。第二条命令的输出可以交给审阅者。审阅 JSON 包含 rows 数组，其中每轮使用 turn_id 和 claims，每条命题记录 observed（true、false 或 null）与 evidence（原答复中的逐字引用或空字符串）。第三条命令核对审阅 JSON，再依据冻结的预期计算分数。

## 单笔提交与页面指引回归

明确申请单笔普通订单退款时，`request_order_refund` 核验订单归属、资格和风险，在同一 SQLite 事务中保存任务和待审批单。失败时回滚草稿和对旧审批的撤销。同一申请重试会返回已有工单，已有资料的修改需要匹配任务版本。本人确认、主管审批和退款执行继续由既有服务处理。

页面从会话历史接口和流式事件读取 `next_steps`。服务端用已认证的工单和券状态生成指引。本人确认绑定现有审批 ID，券复核支持申请时引导联系售后，链接用于查看复核结论。上游凭证更新后会撤下旧指引。模型仍生成自然语言回复。

以下每组各运行一次，调用 DeepSeek `deepseek-chat`（temperature 0，无 SDK 重试，最多 8 次模型调用/轮），每个场景使用独立 SQLite。v2 沿用首轮预期做回归。v3 的 5 个新场景和评分条件在运行前冻结。两组都使用混合任务工具子集，完整生产提示、知识库和浏览器渲染未接入真实模型回放。

| 指标 | v2 首轮 | v2 回归 | v3 首次验证 |
| --- | ---: | ---: | ---: |
| 业务场景通过 | 9/10 | 7/10 | 4/5 |
| 业务轮次通过 | 11/13 | 9/13 | 6/7 |
| 普通退款工单符合预期的轮次 | 11/13 | 13/13 | 6/7 |
| 服务端指引条件符合 | 未记录 | 35/36 | 20/20 |
| 模型调用 | 51 | 43 | 24 |
| 未确认的退款执行、新增争议 | 各 0 | 各 0 | 各 0 |

指引分数逐项检查是否出现预期的审批、撤回、提交争议、等待复核或联系售后动作，包含应出现与应缺席两类条件。新版模型正文未重新做盲审。v2 有一轮只咨询 A400，正文推测将来需要本人确认，但该轮没有工单，页面也没有确认按钮。

- v2 的 A400 场景成功建待主管审批单，并在下一轮撤回。券分支仍待复核。严格业务判分依然失败，因为模型漏记了券分支决策。
- v2 另外两个失败中，一轮模型漏读了用户已经提供的 V400 券号，页面缺少联系售后指引。另一轮观察到券在复核，却没有保存对应分支决策。
- v3 唯一失败轮成功建低风险工单，留存原因是「衣服穿不上，尺码不合适」，严格原因匹配只接受预设别名。同轮也漏记了券分支决策。两条页面指引均符合预期。

首轮和回归修改了工具与提示，两次各采样一次。调用数的差距是本次观测，无法归因给单个改动。

```bash
python -m evaluation.mixed_holdout_eval --with-model --intake --dataset docs/evaluation/mixed-reply-holdout-v2.json --output work/reply-holdout/intake-v2-new.json
python -m evaluation.mixed_holdout_eval --with-model --intake --dataset docs/evaluation/mixed-reply-holdout-v3.json --output work/reply-holdout/intake-v3-new.json
```

每轮 JSON 的 `checks` 保存业务判分，`next_step_checks` 保存页面指引条件判分。v3 数据摘要为 `ee1eae3ed137ee2b1ff9112909796748195788a7d4c1f177b20a5e70723b664c`。
