# 混合售后任务

同一条消息可以同时处理团购券核销查询和一笔普通订单退款。输入示例是「V200 在中心店 CENTRAL 用不了。A300 尺码不合适，请申请退款。」用演示消费者身份发出消息。随后按 Agent 需要提供带时区的到店时间。

券分支先从已有的券号观察事实。服务端直接记录证据充分的解释；其余步骤由 Agent 根据工具返回的下一步和必填字段推进，每个选择都校验当前事实和版本。普通订单继续使用已有的退款工具和确认卡片。用户仍需在工作台确认提交券争议，并在适用时通过原退款审批入口批准普通订单。

| 观察结果 | 处理方式 |
| --- | --- |
| 记录匹配或券已过期 | 说明核查结果 |
| 需要到店信息，仍缺门店或时间 | 只请求缺少的字段 |
| 到店信息齐全，存在核销证据冲突 | 提供预填的团购券争议入口 |
| 已提交争议 | 读取人工复核状态或转述已记录的结论 |

商家补传沿用已有的签名入站和版本校验。聊天在下一次查询时检测证据或争议版本变化，隐藏旧结论，仅刷新受影响的券分支。落库的分支状态按租户、用户和会话隔离，并用版本锁拒绝基于旧证据提出的步骤。当前支持每个混合会话的一个券分支。

## 浏览器离线回放

安装 [README](../README.md#先跑一个示例) 列出的演示依赖，运行命令后打开 [本机演示页](http://127.0.0.1:8765/)。

```bash
python scripts/run_voucher_demo.py --mixed
```

1. 点「发起混合请求」。V200 等待到店时间，A300 同一轮生成待本人确认的工单。
2. 点「补充到店时间」，查看预填的团购券工作台入口，再点「确认提交争议」。V200 进入待人工复核。
3. 点「补传流水并刷新」。展开最后一轮轨迹，旧券步骤收到 conflict，新证据核查为已核销且仍待人工复核。A300 保持原工单号和待确认状态。

页面播放脚本模型在 LangGraph 中发出的工具调用，调用实际的券、证据校验和退款建单服务。演示仅监听本机，使用临时 SQLite 和模拟订单，重启进程可从头开始。

## 配对对照

固定基线先收集到店字段，商家更新后统一读取两条分支。按观察调整的方案先看券的实际证据，按需补问和刷新。两组都用相同的退款、券、人工审批服务和隔离 SQLite，普通退款在券分支等待期间均可推进。每场景每组运行三次，共 12 次。

| 场景 | 补问 固定 / 按观察 | 券观察调用 固定 / 按观察 | 补传后退款状态读取 固定 / 按观察 |
| --- | ---: | ---: | ---: |
| 两端核销记录一致 | 1 / 0 | 1 / 1 | 0 / 0 |
| 记录冲突、提交争议、商家补传 | 1 / 1 | 3 / 4 | 1 / 0 |

数值按单次用例统计。冲突场景中，按观察的方案先诊断再补问，多一次券观察，同时省下一次与事件无关的退款状态读取。12 次都保留同一张待确认退款工单且无审批前退款。冲突样例中，两个方案的过期步骤都被拒绝。

## DeepSeek 试跑

空响应恢复改动后，既有的固定图和模型规划对照试跑 4/4 通过。

新混合场景的前几次试跑出现了重复询问 A300 单号、把 V200 当普通订单查询，以及未初始化券分支时重复问券号。随后澄清订单与券的用途，并让券状态工具返回明确的 not_started 和下一步提示。
最终用同一两轮输入复跑，7 项检查通过。第一轮只补问到店时间，A300 待本人确认。第二轮返回带到店信息的争议地址，保留原退款工单。试跑使用真实模型和业务工具，也保留了先前未通过的报告。这个试跑衡量该路径能否完成，配对表的数据来自上面的确定性对照。

另一组冻结对话对当前版本做了首次真实模型评测，覆盖含糊指代、撤回、证据更新和故障，按数据库与答复分别记录。 [留出评测](mixed-holdout.md)

## 复现

```bash
python -m pytest tests/test_mixed_voucher.py -q
python mixed_eval.py --output work/mixed-agent/comparison.json
python mixed_eval.py --with-model --output work/mixed-agent/live-smoke.json
```

前两个命令使用脚本模型或确定性工具路径。最后一个使用付费 DeepSeek API，在隔离库中对两轮自然语言输入进行试跑。真实模型试跑单独记录，配对表衡量调度策略的查询和补问开销。
