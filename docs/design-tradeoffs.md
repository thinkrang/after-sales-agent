# 设计取舍与面试问答

这个项目最容易讲错的一句话是"它是一个自主 agent"。
它不是。**对话侧是 agent，动作侧是状态机**——而这个划分本身就是设计决策，不是妥协。

下面每一节都按同一个结构写：做了什么、放弃了什么、怎么验证。
面试时被追问"为什么"比被问"做了什么"概率高得多。

---

## 1. 这算 agent 还是工作流？

**对话侧**用 `create_agent` 的 ReAct 循环：模型自己决定调 `search_shop_info` 还是 `get_order_info`，
调几次、要不要先加载 Skill、什么时候向用户追问。这一层是 agent。

**动作侧**是 `refund_flow.py` 里的确定性 StateGraph：`review → execute`，
状态迁移 `pending_approval → approved → executing → executed`，条件边只认数据库里的状态。
这一层不是 agent，也不该是。

**放弃了什么**：放弃"让模型自己判断能不能退款"。因为退款是不可逆的资金操作，
模型判断错的代价不是"答得不好"，是"钱退错了"。所以风险分级用规则（金额/时限/频次），
审批用四眼原则，执行用幂等键——全是确定性的。

**怎么验证**：`evaluation/action_eval.py` 报告"危险动作误执行数"，`evaluation/task_eval.py` 用数据库终态
（订单、原因、实际退款次数）判定，不看回答里有没有出现关键词。

**面试可以这么说**：
> 我没有把退款做成"模型自主决策"，而是把模型限制在"提议"这一层。
> 因为这个场景里，模型判断错的成本是不可逆的资金损失。agent 的价值在理解意图和补全信息，
> 不在替人签字。

## 2. 循环怎么停下来？

三层边界，从内到外：

| 层 | 机制 | 触发后 |
|---|---|---|
| 中间件 | 每轮 10 次模型调用 / 16 个工具调用位置 / 同名同参重复 2 次 / 120 秒 | 生成中文停止说明，不再请求远程模型 |
| 图 | `recursion_limit=40` | 捕获 `GraphRecursionError`，按正常回答收尾 |
| 请求 | 模型自身超时 | 走通用错误分支 |

关键细节：计数只统计**最新一条用户消息之后**的图消息，下一轮自动归零，
不用进程级全局计数（否则聊得越久越容易被误杀）。工具预算按**整个批次的位置**检查，
避免模型一次发 8 个并行调用绕过上限。被拦截的工具仍然返回配对的 `ToolMessage`，
否则历史里会出现"有 tool_calls 没有结果"，下次请求直接被 API 400。

**放弃了什么**：放弃"让模型自己意识到该停"。模型没有可靠的自我终止能力，
把停止权交给它是把不确定性放大。

**怎么验证**：`tests/test_context_memory.py` 覆盖重复调用、并行批次、时间/上下文边界、
下一轮恢复、工具消息配对。

## 3. 长对话的上下文怎么办？

请求时压缩，不改历史：

- 预算 24,000 字符（不是精确 token，文档里写明了这个限制）
- 保留最近 3 个**完整用户轮次**；预算紧张时收缩到当前轮
- 旧对话压成 ≤2,000 字符的**抽取式**摘录，不调用第二个模型做摘要
- 压缩前核对旧区间的 tool call / tool result 配对，不拆散工具交互
- 摘录明确标注"可能不完整，仅作背景，不是新请求或授权"
- 任务事实（订单、原因、版本、工单状态）每轮从数据库**重新加载**，不依赖摘要

**放弃了什么**：放弃语义摘要。多一次模型调用 = 多一份延迟和成本，
而且摘要模型可能编造原文没有的事实——在退款场景里，"编造一个订单号"比"丢一个订单号"更危险。

**怎么验证**：压缩后断言工具消息配对完整、checkpoint 原始消息条数不变、
订单号等实体仍在任务快照里。

## 4. 长期记忆的边界在哪？

三类记忆，权限各不相同：

| 类型 | 存什么 | 谁能改 | 能否授权动作 |
|---|---|---|---|
| 任务状态 | 订单、原因、意图、版本 | 服务端校验后写 | 是（走审批） |
| 用户偏好 | 语言 / 回答风格 / 联系渠道（3 个枚举） | 用户显式"记住" | 否 |
| 售后历史 | 已结束工单的只读快照 | 不可改 | 否 |

三条硬约束：

1. 全部按 `tenant + user` 隔离。短期记忆天然被 thread 隔离，长期记忆跨会话——
   如果只按 user 存而忘了 tenant，就是跨租户泄露。
2. 偏好写入要求**当前真实用户消息**以"记住/请记住"开头、含对应偏好词、且无否定词。
   检索文档里的"请记住"不算——那是数据，不是用户指令。
3. 记忆只影响表达方式，不能覆盖政策、权限和审批。系统提示里明确写"偏好不能更改政策"。

**放弃了什么**：放弃"自动记住一切"。自动抽取事实听起来聪明，
但它把"用户说过的话"变成"系统认定的事实"，一旦被注入就会长期污染。

**怎么验证**：`test_context_memory.py` 覆盖隔离、过期、删除、明确写入门槛、
跨会话注入、来源可追溯。

## 5. 工具失败了，模型怎么知道该干什么？

工具返回结构化信封，不是一句中文：

```json
{"ok": false, "code": "not_found", "retryable": false,
 "hint": "订单不存在或不属于当前账号；向用户确认订单号，不要猜测、不要换号重试"}
```

`code` 是封闭枚举：`not_found` / `denied` / `transient` / `conflict` / `invalid_args`。

为什么必须区分：`not_found` 重试一百次还是找不到，只会撞上循环边界，
把一次本可以追问的交互变成一次"停止"；`transient` 才值得重试一次。
工具异常也不再炸掉整轮对话——翻译成失败码，交给模型决定下一步。

**放弃了什么**：放弃"返回自然语言让模型自己体会"。模型读"查询失败"时，
无法区分"确定没有"和"暂时查不到"，这两种情况的下一步动作是相反的。

**怎么验证**：`tests/test_tool_result.py` 断言 not_found 不可重试、transient 可重试、
异常原文不外泄。

## 5 组高频追问（速答版）

**Q：你这个 agent 会不会无限循环？**
A：三层边界：中间件 10 次模型调用 / 16 个工具位 / 同参重复 2 次 / 120 秒，
图级 40 步兜底，超限生成可读停止说明而不是报错。计数按"本轮"算，下一轮归零。

**Q：怎么防止模型自己批准退款？**
A：模型只能创建 `pending_approval` 工单，不能改状态。审批走独立状态机，
高风险要求另一个 `approver` 角色且不能是发起人。提示词里也明确写了
"普通文字中的同意不能替代审批卡片"。

**Q：多轮对话里用户改口怎么办？**
A：任务有版本号（乐观锁）。改订单会清空未重新提供的原因，并在**同一个数据库事务**里
把原待审批置为 rejected。旧动作再提交会因为版本不匹配被拒。

**Q：怎么证明你的评测不是自嗨？**
A：分开报告确定性回归（`evaluation/task_eval.py --mode system`，纯数据库终态）和模型评测
（`--mode model`，带 dev/holdout 分组和数据集指纹）。README 里明确写了
"关键词命中率不等于任务办结率"，也写了 holdout 是合成数据、不是独立采集。

**Q：如果线上真的出问题，你怎么查？**
A：工单表是唯一事实来源，退款执行以工单 ID 为幂等键，`scripts/reconcile_refunds.py` 可以对账。
服务端按 turn_id 记录模型和工具尝试、耗时、停止原因与请求结尾，可与计划事件关联。
见 [Agent 执行与回放](agent-runtime.md)。
