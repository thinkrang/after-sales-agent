# 任务规划与编排验证记录（2026-11-10）

本记录区分工程契约、真实模型能力和未验证部分。运行数据均使用隔离数据库；
没有修改日常演示订单或把测试工单写进用户业务库。

## 交付范围

- 一会话至多两笔独立退款任务，结构化计划和依赖校验。
- 独立查询并行、逐笔审批，等待主管不阻塞另一笔申请。
- 补信息、换订单、改原因、取消对应分支的局部重规划。
- 持久化抢占、租约、版本隔离、有限重试、总预算、恢复扫描轮转。
- 高风险审批仍受四眼原则约束，结果回写原聊天会话。
- 计划轨迹、审批引用、版本化结果和耗时；多笔审批 UI。
- MCP 独立任务标识与版本修改；核查器故障不再伪装为无证据。

使用方式与设计取舍见 [实现说明](agent-planning.md)。

## 真实模型对照：部分完成

模型：DeepSeek `deepseek-chat`，temperature=0，关闭 thinking，max_retries=0。
4 个开发场景，每方案每场景最多 16 次模型调用；无独立 holdout。
两方案使用相同订单、身份、风险与审批服务；双方都排除 RAG。

基线为现有单任务 ReAct 工具，新方案为生产规划工具。
整个方案同时改变任务状态、工具契约与调度，因此不是对“规划算法”这一单变量的消融。

| 场景 | 原单任务 ReAct | 新规划方案 |
|---|---|---|
| 同时申请两笔 | 未通过：不能同时保留两笔待审批 | 通过：独立审批，两笔最终各退款一次 |
| 只改 A400 原因 | 未通过：不能同时保留两笔待审批 | 通过：A300 保持，A400 旧审批失效 |
| A400 原因稍后补充 | 未通过：不能同时保留两笔待审批 | **未完成：供应商返回 HTTP 402，余额不足** |
| 仅咨询两笔 | 通过：未提交申请 | **未完成：供应商返回 HTTP 402，余额不足** |

新方案是 **2 个已完成场景通过，另 2 个被环境阻断**。
不能把余额不足计为模型规划失败，也不能把未完成场景计为通过。
原始报告 [model-partial.json](evaluation/planning-2026-11-10/model-partial.json)
保留了当时的 `passed=false` 和完整错误字段；解释时必须同时检查错误类型。
后续评测入口已补充 provider 分类及余额/限流等错误后的停止机制，本轮未再次付费调用。

### 调用与开销

以下是已完成配对场景的观察值。延迟为调用到停止/办结的总时间，不含人的审批等待；
失败基线没有完成同样的业务量，不能据此推导生产性能提升。

| 场景/方案 | 模型调用 | Agent 工具调用 | 输入 token | 输出 token | 观察耗时 |
|---|---:|---:|---:|---:|---:|
| 双申请 / ReAct | 4 | 5 | 5953 | 464 | 10.32 秒，未办结 |
| 双申请 / 计划 | 3 | 2 | 8125 | 651 | 4.57 秒，办结 |
| 改原因 / ReAct | 6 | 6 | 10243 | 786 | 9.55 秒，未办结 |
| 改原因 / 计划 | 5 | 3 | 21626 | 882 | 6.84 秒，办结 |

观察到工具调用减少，但结构化契约与计划状态增加了输入 token，不能宣称“更省成本”。
原始 JSON 另记录公共业务接口调用次数，避免把“一次计划工具内的多个业务调用”误算成零开销。

这批模型报告生成于最终扫描公平性、事件结果留存和评测错误分类收尾之前，
保留了当时的源码 hash。最终版本的工程回归已另行运行；最终源码上的完整模型评测尚未重跑。
