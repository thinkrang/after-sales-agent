# 团购券核销争议

消费者说没有到店，平台却显示团购券已核销。先按登录态核对券归属，再比对平台和商家的两份记录。
已核销记录比对状态、核销流水号和时间。评估使用券上记录的规则版本。争议单保留当时使用的规则和两份证据，供人工复核。

| 样例（ACME 客户） | 证据 | 提交后的状态 |
| --- | --- | --- |
| V100 双人咖啡券 | 两边均未核销，券有效 | 已出结论，可申请退款 |
| V200 午餐套餐券 | 平台已核销，商家未核销 | 待人工复核 |
| V300 周末体验券 | 两边的核销流水、时间匹配 | 有消费异议，待人工复核 |
| V400 单人观影券 | 缺商家记录 | 待人工复核 |
| V500 下午茶券 | 两边均未核销，券已过期 | 待人工复核 |

## 演示流程

1. 按 README 启动售后工作台。用 `acme-user / demo1234` 登录，从侧栏打开「团购券争议」。
2. 选择 V200 和「中心店」，点「检查能否使用」。页面会展示平台与商家状态冲突。填写「我已到店，店员说这张券用不了」并确认提交。争议单带上所选门店、到店时间、预约（如有）和核销证据。重复提交返回同一争议单。
3. 用独立的浏览器会话登录 `acme-manager / demo1234`。在「待复核」打开 V200，查看两份记录并填写复核依据。例如模拟已向商家核实未消费，选择「支持申请退款」。
4. 客户刷新争议列表后打开详情，查看结论、复核依据和处理记录。也可以在聊天中输入「我在中心店 CENTRAL，V200 用不了」，Agent 会用查券工具生成带券号、门店和时间的工作台链接。

用 V100 还可以看两个分支。中心店晚上 20:00 起不在券的使用时段内。公园店需要确认预约，系统可列出券允许的时段供用户确认。
这些时段来自模拟券规则，可预约库存由商家另行确认。

样例规则与证据均由本地 SQLite 模拟。这里的结论支持售后进一步处理，系统只记录审核结果。真实业务仍需接入可信的券平台、商家核销服务和独立的退款执行流程。

## 离线浏览器演示

演示服务使用现有争议页和真实案件 API，启动时创建临时 SQLite，仅监听本机地址。无需模型 API Key。

```bash
python -m pip install "fastapi==0.147.0" "uvicorn==0.54.0" "pydantic==2.13.5" "python-dotenv==1.2.3"
python scripts/run_voucher_demo.py
```

1. 打开 [本机演示](http://127.0.0.1:8765/)。点「以消费者身份打开」，填写到店说明并确认提交 V200。
2. 返回演示首页，点「以主管身份打开」，从「待复核」进入 V200。保留这个详情页。
3. 在另一个标签页打开演示首页，点「补传商家流水」。再点一次可看到重复事件被忽略，点「发送旧版本」可看到乱序事件被忽略。
4. 回到主管详情页，用原页面尝试提交，系统会提示争议单已更新。点「刷新」后基于新记录复核。最后切回消费者身份打开原争议单查看结果。

重新启动演示会使用一份新的临时数据库。

## 核销规则离线回放

```bash
python scripts/replay_voucher_policy.py --output-dir work/voucher-policy-replay
```

同一份证据快照与同一判定时间分别运行 5 分钟和 2 分钟规则。输出 replay.json 和 replay.md。
报告区分核查建议、初始案件分流、与模拟标签的偏差，并列出应抽查的案件编号。
18 份快照中有 4 份建议变化，初始分流变化为 0。收紧容差在这批模拟数据里减少了对证据吻合的误提示，也增加了漏提示。
原始输入与标签见 [合成样本](evaluation/voucher-policy-fixtures.json)，逐案输出见 [回放报告](evaluation/voucher-policy-replay-2026-11-17.md)。
同一输入重复运行，JSON 和 Markdown 两份报告的 SHA-256 一致。

## 商家补传与复核

模拟商家可调用 POST /voucher-evidence/{tenant}/merchant。服务端从环境变量 VOUCHER_MERCHANT_KEYS 按 URL 租户读取独立密钥。
发送方使用 X-Voucher-Timestamp 传 Unix 秒，并把 HMAC-SHA256 十六进制签名放进 X-Voucher-Signature。
签名输入为 tenant、点号、timestamp、点号与原始请求体依次拼接。每次重发可刷新签名时间，保留 event_id。
载荷包含 event_id、voucher_id、source_version、record_id、status。已核销需同时提供 redeem_ref 和带时区的 redeemed_at。

事件、最新商家记录和受影响案件使用同一个 SQLite 事务。重复事件和较旧的来源版本不会改动快照。
待复核单会更新证据和案件版本。已结案的单转为待重新复核，原结论与依据可在历史记录查看。
测试先保存审核员持有的旧版本，再补传 V200 核销流水，验证旧提交返回 409，另一张券以及另一租户的同号券保持原版本。

## 权限与一致性

- 发起人只能核查自己的券、提交自己的争议和查看自己的结果。审批员只能复核同租户其他发起人的单子。
- 每个租户下每张券至多一张争议单。正式提交保存证据快照、规则版本、处理依据和时间。
- 复核提交携带案件版本，服务端在事务内同时确认案件和证据仍与页面一致。记录已变化时，先点「重新核查证据」更新快照，再决定。
- 并发复核只有一个请求能结案。提交、证据更新和结案都有事件，同一张单可追溯到每次使用的证据。
- `voucher-v1` 允许两个核销时间相差 5 分钟，`voucher-v2` 为 2 分钟。测试用 3 分钟差值验证版本生效。

## 本地验证

无需模型 API Key 即可运行 HTTP、SQLite 和权限回归：

```bash
python -m pytest tests/test_voucher_disputes.py -q
```

已有完整项目依赖时，可以进一步验证真实聊天图调用只读工具，模型由脚本代替：

```bash
python -m pytest tests/test_task_http.py::test_chat_can_check_voucher_without_creating_a_case -q
```

完整 pytest 为 336 项通过、1 项跳过、2 项未选中。覆盖规则回放、归属、缺失证据、冲突、重试、旧版本拒绝、自批阻断和审批并发。
Chrome 使用临时数据验证了 V200 链接预填、客户提交、商家签名补传、旧审批被拒、主管刷新后复核和客户查看结果。
到店检查和补传事件可直接在临时数据上复现：

```bash
python -m pytest tests/test_voucher_disputes.py -k "visit_guidance or late_merchant_event" -v
```
